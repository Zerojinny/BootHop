# BootHop — notes for development

A small Windows tool that makes the **next start of the PC (once) from an image of a WIM file in a RAM disk, or from the Windows in a VHD / VHDX**. It began as the "Boot once from this WIM" feature of WimSmith (the right-click menu item `ramboot`, `src\ramboot.cpp` + `RamBoot` in `src\helper.cpp` of `F:\Sync\wimsmith_1.3`, a separate project) as its own exe. WIM files are read and changed with `wimgapi.dll` of Windows (System32, also in Windows PE; the library DISM uses), not wimlib.

## What it does

- `BootHop.exe` without a file: the list window (`src\bootlist.cpp`, `RunBootList`, the main window `ui::Main`): the files to boot once from, kept in `BootHop.list` next to the exe (UTF-8 with BOM, one full path per line, written at each change). [Add...] (Insert) picks files with the own file dialog (`OpenFiles`), [Remove] (Del), [Boot once] (double click, Enter) runs `RunOneTimeBoot` on the chosen one; the window stays open after it. `BootHop.exe --add <file>` (the menu item "Add to the boot list") adds the file and opens the window with it chosen; only one list window at a time: a named mutex `Local\BootHop.List` and the window property `BootHop.List`; a later process (several files chosen in Explorer start one each, also a start without a file) hands its path to the open window by `WM_COPYDATA` and brings it to the front. A missing file shows `(missing)` in the size column. The top windows of `ui.cpp` do not give the focus back to a control on activation, so the list window does that itself (`KeepFocus` subclass).
- `BootHop.exe <file.wim>` (or drop a file on the exe, or the right-click menu): checks the header of the file first (`BadHeader` in ramboot.cpp, for all three types: empty = `rb.empty_file`, else `MSWIM\0\0\0` / `vhdxfile` / the VHD footer `conectix` = `rb.bad_header`; wimgapi only says ERROR_BAD_FORMAT (11) for an empty file, seen 2026-11-12), reads the file with wimgapi (unelevated), lets the user choose an image when there are several (the boot image chosen first), warns when it is not Windows PE (`InstallationType` not `WindowsPE` and no `\Windows\System32\winpeshl.exe` in the image: a PE built from install.wim, like PhoenixPE, keeps `Client` in its XML, seen 2026-11-13; a regular install.wim has no winpeshl.exe), checks before the UAC prompt that the image has the loader of this firmware (`wg::HasFile` with `missing`, `FirmwareUefi()` of settings.cpp; refused when surely missing), warns when the drive of the WIM is BitLocker-encrypted (`BitLockerOn`: the shell property `System.Volume.BitLockerProtection`, read unelevated; 1, 3-6 = encrypted, 2 off, 0 not encryptable) and when the WIM + 1 GB is more than the installed memory (`GlobalMemoryStatusEx`), confirms, then runs the elevated helper with a small marquee window, and asks to restart (`shutdown /r /t 0`).
- The helper (`BootHop.exe --helper <work folder>`, job.ini in `%TEMP%\BootHop_job\<time>`, mode `ramboot`, keys `wim`, `index`, `set_boot`, `name`, `copy_sdi`): checks the drive (local, not ReFS) and `\Windows\System32\Boot\winload.efi|.exe` in the image, makes the image the boot index when `set_boot = 1` (`WIMSetBootImage`, checked by reading the header again), takes boot.sdi (the empty RAM disk) from Windows: `SystemBootSdi()` (settings.cpp) = `<Windows>\Boot\DVD\EFI|PCAT\boot.sdi` or `Boot\PXE`, only on a fixed NTFS / FAT drive and not in Windows PE (`MiniNT` key: X: is gone at the next start), so `ramdisksdidevice` is that drive and nothing is written next to the WIM (the default since 2026-11-12; earlier it was always copied); with the setting "copy boot.sdi" on (the window: `CopySdiSetting`, HKCU `Software\BootHop`, DWORD `CopySdi`, the check box `ob.copy_sdi` of the list window; the command line: only `/boot ... /copysdi` = `BootOptions.copySdi`, the saved setting is not read), or when there is no usable one, boot.sdi next to the WIM is used and copied there when missing (as WimSmith does). The GUI decides the same way for the confirmation text and the cleanup and passes `copy_sdi` in job.ini. Then bcdedit: a device object `{7a3c1e52-...9e12}` and an osloader `{7a3c1e52-...9e11}` (the same fixed ids as WimSmith, deleted and made again each time, not in the display order), then `/bootsequence`. The work folder is deleted after success and kept after a failure (the last lines of status.txt are shown).
- **`.vhd` / `.vhdx`** (native VHD boot, BootHop only): the GUI checks that the file is on a local NTFS drive, warns on a BitLocker drive (`vb.bitlocker`: Windows does not support native VHD boot there) and confirms (no wimgapi, no image choice, no boot.sdi). The helper mode `vhdboot` (keys `vhd`, `name`; `VhdBoot` in helper.cpp) loads `virtdisk.dll` at run time, opens the file read-only (`OPEN_VIRTUAL_DISK_VERSION_2`; a sharing violation = attached elsewhere), refuses a dynamic / differencing VHD when the drive has less free space than it grows by (virtual - physical size: it expands to full size at the start), attaches it read-only without drive letters (unless already attached; then it stays attached), waits up to 20 s for a volume with `Windows\System32\Boot\winload.efi|.exe`, and makes an osloader `{7a3c1e52-...9e13}` with `device` / `osdevice vhd=[D:]\path.vhdx` (no locate element: the boot manager finds the partition in the VHD that holds the application path / systemroot, so a VHD with an EFI, MSR and Windows partition works too; bcdboot writes the same with `locate=custom:12000002`), `path`, `systemroot`, quietly `inherit {bootloadersettings}` and `nx OptIn`. Then `/bootsequence`; the VHD is detached at the end. Each job deletes all three fixed ids first, so only one BootHop entry exists.
- **Command line** (`src\cli.cpp`, `RunCli`; any first argument starting with `/`): **BootHop.com is used on its own, independent of BootHop.exe** (the user's rule, 2026-11-12): it works without the .exe next to it, its options are given per run, and it reads neither `BootHop.ini` (main.cpp: a first argument `/...` loads the language of Windows, no theme) nor a setting the window saves, and has no commands for them (`/menu` and a `/copysdi on|off` setting were removed again). `BootHop /boot <file> [/index N] [/restart] [/copysdi [/deletesdi]]` (`/deletesdi` = `BootOptions.deleteSdi`, the per-run form of `delete_sdi`; no question and no window: `RunOneTimeBootQuiet` sets `quiet` in ramboot.cpp, so `Tell` / `Ask` print instead of a message box and count a question as yes; a WIM with several images takes `/index`, else its boot image), `BootHop /status` (helper mode `status`: `bcdedit /enum {bootmgr} /v`, the `bootsequence` element and its continuation lines, STATE lines per fixed id; elevated too, the BCD cannot be read otherwise),  `BootHop /cancel` (mode `cancel`: `/bootsequence <id> /remove`, then all three ids deleted), `/?`. Exit codes: 0 done (/status: pending), 1 failed (/status: none), 2 wrong arguments, 1223 UAC cancelled. The texts are `cli.*`; their language follows only the console code page (`PickLanguage`, after `OpenConsole`): Korean on 949 / 1361, English on code pages without Hangul, the language of Windows on 65001; `language` of `BootHop.ini` is not read. `cli.usage` loses leading spaces in the language file, so `Usage` indents the lines under each line starting with `BootHop `. `build.bat` links the same objects twice: `BootHop.exe` (`/SUBSYSTEM:WINDOWS`) and `BootHop.com` (`/SUBSYSTEM:CONSOLE /ENTRY:wWinMainCRTStartup`): a command prompt runs the .com for `BootHop` (it waits, `%errorlevel%`); the .exe attaches to the parent console but the prompt does not wait. `GuiExe()` (settings.cpp) gives BootHop.exe also when the .com runs, for the menu commands, the cleanup Run value and the elevated helper (`ShellExecuteEx` with `runas` on a `.com` fails with ERROR_NO_ASSOCIATION 1155, seen with `/status`: the class `comfile` has no `runas`). **BootHop.com also works alone** (no BootHop.exe next to it; `GuiExe()` then gives the .com): the helper is started with `SEE_MASK_CLASSNAME` + `lpClass = "exefile"`, whose `runas` is `"%1" %*` (tried with `open`: the .com starts with its arguments); the menu commands and the Run value point to the .com, and `DropOwnConsole` (main.cpp: `GetConsoleProcessList` = 1, i.e. not started from cmd) frees the console before the GUI / `--cleanup`, so no empty console window stays (tried: only the list window is shown).
- Deleting a copied boot.sdi after the restart: the check box `ob.delete_sdi` of the list window (HKCU `Software\BootHop`, DWORD `DeleteSdi`, `DeleteSdiSetting`; without that value `delete_sdi` of `BootHop.ini` as before; enabled only while boot.sdi is copied: copy on, or no usable one of Windows); the command line: `/deletesdi`: a boot.sdi it copied gets a value `BootHop.DeleteBootSdi` under HKCU `...\CurrentVersion\Run`: `BootHop.exe --cleanup <sdi> <boot time>` deletes the file and the value at the first logon whose boot time differs by 10 s or more.
- `BootHop.ini` next to the exe (written by hand, read only; the window only, not the command line): `language = en | ko`, `theme = dark | light`, `delete_sdi = 0 | 1` (only until the check box is used). Settings BootHop changes itself are not in it: the right-click menu (its registry keys), copying and deleting boot.sdi (HKCU `Software\BootHop`).
- The list window has a row of options above its buttons: the right-click menu, copying boot.sdi, deleting it after the restart. Files dropped on it from Explorer are added (`DragAcceptFiles`, `WM_DROPFILES` in the `KeepFocus` subclass). Its top row shows the hint, or the start made last while it is pending (`PendingBoot()` of ramboot.cpp: HKCU `Software\BootHop` `PendingFile` + `PendingBootTime`, written by every successful job, also of the command line; dropped when the boot time of Windows differs, i.e. after a restart, and by a cancel or a `/status` that finds none) with [Cancel it] (`RunBootState(true, true)`: the cancel helper with the marquee window and a message box). The window does not read the BCD itself (that needs elevation). The right-click menu is turned on / off with the check box of the list window (`ob.menu_on`, `SetContextMenu`); the registry keys themselves are the setting (`ContextMenuOn`: the `.wim` item or the background item is there), no `BootHop.ini` key. While it is on, each start of the GUI (not `--helper` / `--cleanup` / a command) makes again, only when they differ, the two right-click menu items of `.wim`, `.vhd`, `.vhdx` (HKCU `Software\Classes\SystemFileAssociations\<ext>\shell\BootHop` = `ob.menu`, `"BootHop.exe" "%1"`; `...\shell\BootHop.Add` = `ob.menu_add`, `"BootHop.exe" --add "%1"`; and `ob.menu_list` in the menu of the empty space of a folder and of the desktop, HKCU `Software\Classes\Directory\Background\shell\BootHop.List`, `"BootHop.exe"` (the list window); written again only when the exe path or the language changed); turned off, all of them are removed (`src\menu.cpp`). WimSmith's own `WimSmith >` menu of `.wim` is a separate key.
- **wimgapi** (`src\wimg.cpp`, namespace `wg`): `wimgapi.dll` loaded at run time from System32 (`LOAD_LIBRARY_SEARCH_SYSTEM32`), the declarations of the ADK's wimgapi.h written in the file (no ADK needed to build). `ReadInfo`: `WIMCreateFile` (read) + `WIMGetAttributes` (`WIM_INFO`: image count, boot index, parts) + `WIMGetImageInformation` (XML: `NAME`, `INSTALLATIONTYPE`); works unelevated. `HasFile` (the loader in the image): `WIMLoadImage` + `WIMExtractImagePath` (undocumented, exported since Windows 7) into `<work>\wimtemp` (`WIMSetTemporaryPath` first), the file deleted again; flags must be 0 (`WIM_FLAG_NO_DIRACL|NO_FILEACL` = ERROR_INVALID_PARAMETER); unelevated a file that is there gives ERROR_PRIVILEGE_NOT_HELD 1314 (its security cannot be set), counted as there, a missing one ERROR_PATH_NOT_FOUND. `SetBootImage`: `WIMCreateFile` (read/write) + `WIMSetBootImage`, then read again to check. Tried on 2026-11-12 with a PhoenixPE Boot.wim (and a copy for the boot index). wimlib (and its download, `libs.cpp` / `unzip.cpp`) was removed on 2026-11-12.

## Build

```
build.bat
```

Compiles `src\*.cpp` once and links `BootHop.exe` (window) and `BootHop.com` (console, the command line) (x64, static C runtime) with the Visual C++ of Visual Studio 2017 or later, like WimSmith's `build.bat`. `lang\*.ini` are embedded.

## Working on it

- BIOS (legacy) PCs: the WIM (RAM disk) boot confirmed working by the user on 2026-11-12 (`FirmwareUefi()` false: `winload.exe`, the same `/bootsequence`); the VHD boot on BIOS not tried yet (VHD boot confirmed on UEFI only).
- BitLocker: not tested on an encrypted drive (none on the development PC, 2026-11-12); `SystemBootSdi()` skips a BitLocker Windows drive (boot.sdi then copied next to the WIM).
- **The name was OnceBoot until 2026-11-12** (the project folder is still `onceboot`; the language keys keep the prefix `ob.`). Each start of the window program (`TakeOverOldName`, main.cpp; not a command of the .com) moves `OnceBoot.list` / `OnceBoot.ini` to the new names when those are missing, takes `CopySdi` of HKCU `Software\OnceBoot` and deletes that key, and rewrites a pending `OnceBoot.DeleteBootSdi` Run value as `BootHop.DeleteBootSdi` with this exe; `UpdateContextMenu` removes the old menu keys (`shell\OnceBoot`, `OnceBoot.Add`, `OnceBoot.List`) and makes the new ones when they were there. The BCD ids `{7a3c1e52-...}` stayed the same, so `/status` and `/cancel` also find entries made by OnceBoot.
- Source files use CRLF line ends; language files are UTF-8 with BOM.
- In the Git Bash of this PC `sed -i` drops the CR of every line it touches (whole file), and `grep -c $'\r$'` does not see CRs (it counts every line): edit with Python (`newline=''`) and check for bare LFs with the regex `rb'(?<!\r)\n'` (seen 2026-11-12).
- No PowerShell at run time; it runs in a WinPE too (its own file dialog).
- VHD boot, tried on 2026-11-12 (a GPT `w11.vhd` with an EFI and a Windows volume): `bcdedit /set ... device partition=\Device\HarddiskVolume<n>` of the attached VHD is accepted but stored as a plain partition (`/enum` shows no `vhd=`), which is not there at boot; so `vhd=[D:]\path` is set directly, and with it the PC started from that VHD (confirmed 2026-11-12).
- Testing the command line: `.\BootHop /?` and the argument errors run unelevated; `/status`, `/cancel` and `/boot` with a real file start the helper elevated (UAC), so not from a test. In the Claude Code shell `NoDefaultCurrentDirectoryInExePath=1`: call `.\BootHop`, not `BootHop`.
- Testing: never start the elevated part from a test (the UAC prompt and bcdedit change the real PC). The helper can be run unelevated (`BootHop.exe --helper <folder with job.ini>`): it gets to bcdedit and fails there with access denied, which tests everything before it.
